# Планирование: анализ, идентификация проблем и поиск решений

## Проблемы системы

У компании хватает производственных мощностей, но заказы задерживаются в информационных системах. После открытия партнёрского API ситуация ухудшилась. В первую очередь нужно выяснить, на каких этапах останавливаются заказы. Без метрик и кода причины можно только предположить.

| Проблема | Возможная причина или риск |
| --- | --- |
| Заказы не выполняются месяцами вместо обещанных трёх недель | Потерян переход между этапами, не обработано сообщение или заказ долго не назначается оператору. |
| B2B-заказ появляется в CRM только после сообщения от MES | Ошибка доставки или обработки оставит заказ только в MES. Повторная доставка может создать дубликат. |
| Расчёт цены занимает 2–3 минуты, иногда до 30 минут | Расчёты могут занимать ресурсы MES, нужные для интерфейса и обработки статусов. После открытия API таких расчётов стало больше. |
| Первая страница MES медленная даже с фильтром и пагинацией | Нужно проверить запросы, индексы, сортировку, блокировки БД и размер ответа. Одна пагинация не устраняет дорогой запрос. |
| Операторы предпочитают новые заказы | Старые и сложные заказы могут оставаться без исполнителя. При одновременном назначении возможна гонка. |
| По одному экземпляру приложений и БД | Отказ или обновление узла может остановить часть процесса. Чтение и запись конкурируют за одну БД. |
| Shop API и CRM API используют общую Shop DB | Изменения схемы требуют согласования, а нагрузка одного приложения влияет на другое. |
| Проверки и выпуск в release/prod выполняются вручную | Ошибки находят поздно, исправления долго не доходят до пользователей. |
| MES поддерживает один разработчик C# | Доработки MES и текущая поддержка конкурируют за его время. |

## Инициативы и приоритеты

| Приоритет | Инициатива | Что сделать и зачем |
| --- | --- | --- |
| 1 | Найти и разбирать зависшие заказы | Ввести общий `order_id`, историю статусов и контроль возраста заказа. Начать мониторинг, логи и трейсинг с MES — RabbitMQ — CRM. Составить список просроченных заказов и назначить ответственного за каждый. Это позволит помогать клиентам уже во время технических доработок. |
| 2 | Сделать обмен CRM и MES надёжным | Использовать устойчивые очереди, сохраняемые сообщения, подтверждение публикации и подтверждение обработки после записи в БД. Добавить ограниченные повторы, очередь ошибок и защиту от повторной обработки по `event_id`. Запись заказа и события для отправки выполнять в одной транзакции через outbox. Периодически сверять заказы между системами. |
| 3 | Ускорить работу MES | Проверить SQL и индексы дашборда, затем добавить кеш первой страницы. Вынести расчёт цены в фоновый обработчик с ограниченной параллельностью: API принимает задание и возвращает его номер, результат запрашивается отдельно. Назначать заказ атомарно в БД, показывать просроченные заказы отдельно. |
| 4 | Сократить задержки релизов | Автоматизировать основные сценарии B2C/B2B, обмен сообщениями и повторное назначение заказа. Подготовить одинаковый порядок выпуска и отката для release/prod. |
| 5 | Повысить доступность | Проверить резервные копии и восстановление. Затем добавить резервирование БД и вторые экземпляры API там, где это оправдано нагрузкой и ценой простоя. |

Подтверждение публикации означает приём сообщения брокером, а подтверждение обработки — успешную работу потребителя; нужны оба механизма. Их назначение описано в [документации RabbitMQ](https://www.rabbitmq.com/docs/confirms).

## Что выбрать, если можно выполнить только три пункта

Выбираю инициативы 1–3. Первая даёт данные о причинах задержек и помогает разобрать уже накопленные заказы. Вторая устраняет риск разрыва процесса между MES и CRM. Третья сокращает ожидание расчёта и время работы операторов. Добавление серверов без этих изменений может только отложить повторение проблем.

В первые два месяца основной упор — диагностика и обмен сообщениями. В третий и четвёртый — фоновый расчёт и оптимизация дашборда. В пятый и шестой — кеш, проверка под нагрузкой и исправления по результатам. Изменения выпускаются небольшими частями раз в спринт. Проверки затронутых сценариев входят в каждую инициативу; полная автоматизация релизов остаётся отдельной работой.

## Целевая архитектура через полгода

Магазин, CRM и MES сохраняются. Переписывать приложения или разделять их на множество сервисов не требуется. Shop API и CRM API пока используют общую БД; изменения таблиц согласуются между командами. MES хранит производственные данные в своей БД, а тяжёлый расчёт выполняется отдельным фоновым процессом.

CRM и MES обмениваются событиями через RabbitMQ с подтверждениями и повторной обработкой без дубликатов. Состояние заказа можно восстановить по истории, а задержки видны в мониторинге. Дашборд MES использует оптимизированный запрос и небольшой серверный кеш. Правила назначения проверяются в БД независимо от кеша.

Java-разработчики отвечают за магазин, CRM и обмен; C#-разработчик с тимлидом — за MES. DevOps подключает инфраструктуру наблюдения, QA проверяет оба канала заказов и сбои доставки, фронтенд-разработчик дорабатывает дашборд. Новых сотрудников на первом этапе не закладываю. Если поддержка MES продолжит блокировать план, обоснован наём ещё одного C#-разработчика.
