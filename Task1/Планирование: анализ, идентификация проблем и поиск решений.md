# Планирование: анализ, идентификация проблем и поиск решений

## Проблемы системы

Производственных мощностей хватает, но заказы задерживаются. После открытия партнёрского API жалоб стало больше. Начать нужно с проверки пути заказа между системами. Причины в таблице — предположения, которые предстоит проверить.

| Проблема | Возможная причина или риск |
| --- | --- |
| Заказы не выполняются месяцами вместо обещанных трёх недель | Потерян переход между этапами, не обработано сообщение или заказ долго не назначается оператору. |
| B2B-заказ появляется в CRM только после сообщения от MES | Ошибка доставки или обработки оставит заказ только в MES. Повторная доставка может создать дубликат. |
| Расчёт цены занимает 2–3 минуты, иногда до 30 минут | Расчёты могут занимать ресурсы MES, нужные для интерфейса и обработки статусов. После открытия API таких расчётов стало больше. |
| Первая страница MES медленная даже с фильтром и пагинацией | Нужно проверить запросы, индексы, сортировку, блокировки БД и размер ответа. Одна пагинация не устраняет дорогой запрос. |
| Операторы предпочитают новые заказы | Старые и сложные заказы могут оставаться без исполнителя. При одновременном назначении возможна гонка. |
| По одному экземпляру приложений и БД | Отказ или обновление узла может остановить часть процесса. Чтение и запись конкурируют за одну БД. |
| Shop API и CRM API используют общую Shop DB | Изменения схемы требуют согласования, а нагрузка одного приложения влияет на другое. |
| Проверки и выпуск в release/prod выполняются вручную | Ошибки находят поздно, исправления долго не доходят до пользователей. |
| MES поддерживает один разработчик C# | Доработки MES и текущая поддержка конкурируют за его время. |

## Инициативы и приоритеты

| Приоритет | Инициатива | Что сделать и зачем |
| --- | --- | --- |
| 1 | Найти зависшие заказы | Связать операции общим `order_id` и сохранять историю статусов. Начать с логов и метрик пути MES — RabbitMQ — CRM, затем добавить его трейсинг. Передавать список просроченных заказов продавцам для разбора. |
| 2 | Сделать обмен CRM и MES надёжным | Настроить сохранение сообщений, подтверждения доставки и обработки, ограниченные повторы и очередь ошибок. Исключить повторную обработку по `event_id`. Сохранять заказ и событие в одной транзакции через outbox. |
| 3 | Ускорить дашборд MES | Проверить SQL и индексы, сократить ответ и добавить кеш первой страницы. При назначении проверять в БД, что заказ ещё свободен. |
| 4 | Разгрузить расчёт цены | Если замеры подтвердят влияние расчётов на MES, вынести их в фоновый обработчик с ограниченным числом одновременных задач. API возвращает номер задания, результат запрашивается отдельно. |
| 5 | Сократить задержки релизов | Автоматизировать основные сценарии B2C/B2B и сбои обмена. Описать выпуск и откат для release/prod. |
| 6 | Повысить доступность | Проверить восстановление из резервных копий. Добавить резервирование БД и вторые экземпляры API с учётом нагрузки и цены простоя. |

В RabbitMQ нужны оба [подтверждения](https://www.rabbitmq.com/docs/confirms): от брокера при публикации и от потребителя после записи в БД. Outbox хранит события для отправки, если приложение завершилось между сохранением заказа и публикацией.

## Что выбрать, если можно выполнить только три пункта

Выбираю инициативы 1–3. Сначала нужно найти застрявшие заказы и помочь клиентам, затем исправить обмен между MES и CRM и ускорить работу операторов. Перенос расчёта цены в фон оставляю следующим пунктом: он требует изменения API, а влияние вычислений на остальные операции ещё нужно измерить.

В первые спринты добавляем логи и метрики, разбираем текущие задержки. Далее исправляем доставку сообщений и подключаем трейсинг выбранного пути. Оставшееся время полугодия отводим на дашборд, кеш и проверку под нагрузкой. Для каждого изменения QA проверяет затронутые сценарии; расширение автотестов и автоматизация релизов идут отдельной инициативой.

## Целевая архитектура через полгода

Сохраняем магазин, CRM и MES. Shop API и CRM API используют общую БД, MES — свою. Java-разработчики согласуют изменения общей схемы. Расчёт цены остаётся в MES; его перенос в фон относится к следующей инициативе.

CRM и MES обмениваются событиями через RabbitMQ с подтверждениями и повторной обработкой без дубликатов. Состояние заказа можно восстановить по истории, а задержки видны в мониторинге. Дашборд MES использует оптимизированный запрос и небольшой серверный кеш. Правила назначения проверяются в БД независимо от кеша.

Java-разработчики отвечают за магазин, CRM и обмен; C#-разработчик с тимлидом — за MES. DevOps настраивает сбор данных, QA проверяет оба канала заказов и сбои доставки, фронтенд-разработчик дорабатывает дашборд. Работы планируем на текущую команду. Если поддержка MES будет постоянно задерживать доработки, понадобится ещё один C#-разработчик.
