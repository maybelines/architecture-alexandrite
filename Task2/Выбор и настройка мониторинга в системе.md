# Выбор и настройка мониторинга в системе

## Мотивация

Яндекс Метрика показывает поведение посетителей сайта, но не объясняет задержки внутри MES и CRM и не охватывает партнёрский API. Мониторинг нужен, чтобы замечать рост очередей, ошибки и просроченные заказы до жалоб клиентов. Для бизнеса это возможность удержать контракты и направить разработчиков на подтверждённые причины задержек.

## Выбор подхода к мониторингу

Для Shop API, CRM API и MES API выбираю **RED**: частота запросов, ошибки и длительность. Так можно увидеть, какое приложение замедлилось после роста B2B-нагрузки. Такой же подход подходит для обработчиков сообщений и расчёта цены.

Для ресурсов серверов и БД использую **USE**: загрузка, насыщение и ошибки. Например, загрузка CPU показывает занятость, а очередь задач и ожидание соединений — нехватку ресурсов. RabbitMQ проверяем по очередям, скорости обработки и сбоям доставки.

## Метрики

У всех метрик есть ярлык `env`. Для приложений добавляем `service`, для ресурсов — `instance`. В таблице указаны дополнительные ярлыки. Идентификаторы пользователей, заказов и трасс в ярлыки не включаем: они создадут слишком много временных рядов. Их используем в логах и трейсинге.

| Где | Что измерять | Зачем | Дополнительные ярлыки |
| --- | --- | --- | --- |
| Все три API | Число запросов и RPS | Видеть нагрузку и всплески; отдельно учитывать партнёрский трафик MES. | `method`, `route`, `channel` (`b2c`, `b2b`, `internal`) |
| Все три API | Число ответов по HTTP-коду и долю 5xx | Отличать успешные запросы от ошибок. Отдельные счётчики для 200 и 500 не нужны. | `route`, `status_code` |
| Все три API | Гистограмму времени ответа, p95 | Найти медленные операции, особенно получение списка MES. | `route`, `method` |
| Серверы приложений | CPU, используемую память, перезапуски и OOM | Проверять, хватает ли ресурсов и не падают ли процессы. | `service`, `instance` |
| Shop DB и MES DB | CPU, память, занятое и свободное место | Заранее замечать перегрузку и заполнение диска. Shop DB обслуживает также CRM. | `database` |
| Shop DB и MES DB | Активные соединения, долю от лимита, ожидание соединения, блокировки и медленные запросы | Найти насыщение БД и причину задержек API. | `database`, `operation` для измерений в приложении |
| RabbitMQ | Сообщения `ready` и `unacked`, скорость публикации и подтверждения обработки | Отличать накопление очереди от сообщений, уже взятых потребителями. | `vhost`, `queue` |
| RabbitMQ | Число сообщений в очереди ошибок, повторные доставки | Найти события, которые не удалось обработать. Считаем сообщения в DLQ, поскольку exchange их не хранит. | `vhost`, `queue` |
| MES | Длительность и ошибки расчёта цены, число ожидающих и выполняющихся расчётов | Разделить время ожидания и вычисления, оценить влияние сложных моделей. | `outcome`, `complexity` (`simple`, `complex`) |
| Заказы в CRM/MES | Принятые заказы по каналам, количество и возраст заказов по статусам, число просроченных | Увидеть, где останавливается процесс, даже если API отвечает без ошибок. | `channel`, `status` |

`route` — шаблон вроде `/orders/{id}`, а не URL с номером заказа. Время расчёта цены измеряется отдельно от HTTP-запроса: после перевода расчёта в фон быстрый ответ API не означает готовый результат.

Бизнес-показатели получаем периодическим запросом к данным заказов и истории статусов. За принятый B2C-заказ считаем `SUBMITTED`, за B2B — сохранённый заказ в MES; создание его копии в CRM не увеличивает счётчик. Просрочку определяем по обещанной дате получения, по умолчанию — три недели от принятия. `SHIPPED` ещё не означает получение клиентом; окончание процесса — `CLOSED`. Незавершённые корзины в просрочку не входят.

RPS по каждому пользователю, число сессий и объём HTTP-трафика пока не собираем: они не помогают в первую очередь найти причину зависания заказа. Размер S3 можно добавить позднее для контроля расходов; сейчас важнее БД, очереди и MES.

## План действий

1. DevOps разворачивает Prometheus, Grafana и Alertmanager в закрытой сети. На старте метрики хранятся 30 дней.
2. Java-разработчики подключают метрики Spring Boot через Actuator/Micrometer, C#-разработчик — метрики MES с выдачей в формате Prometheus. Метрики серверов собирает node_exporter, RabbitMQ — его Prometheus-плагин. Для managed PostgreSQL используем метрики облака; ожидание запросов дополнительно измеряем в API.
3. Разработчики добавляют метрики расчёта цены и агрегаты по заказам. Технические метрики собираются каждые 15 секунд, бизнес-показатели пересчитываются раз в минуту. Время последнего пересчёта тоже контролируется.
4. В Grafana создаются три дашборда: прохождение заказов, API и расчёты, инфраструктура. Отдельно сравниваются B2C и B2B.
5. Настраиваем начальные алерты: появились сообщения в DLQ; 5xx выше 1% в течение пяти минут при достаточном трафике; очередь растёт, а обработка остановилась; появились просроченные заказы. Технические сбои получает инженер, задержки заказов — также ответственный продавец. Порог ошибок уточняем после недели наблюдений.
6. QA на release проверяет сбой потребителя, ошибку расчёта и задержку заказа: метрика должна измениться, уведомление — прийти ответственному. После этого включаем сбор в prod.
